# AA GUNMAN

[![CI](https://github.com/vocabuki-io/AAgunmandemo/actions/workflows/ci.yml/badge.svg)](https://github.com/vocabuki-io/AAgunmandemo/actions/workflows/ci.yml)

**▶ 遊ぶ: https://vocabuki-io.github.io/AAgunmandemo/**

マウスの視点操作にポインタロックを使うので、iframe の中ではなく直接開くこと。

単三電池（AA）をリボルバーに装填して撃つ、ブラウザで動く TPS アリーナシューター。
弾は電気。**ボルト(V)** と **アンペア(A)** を溜めて配合し、状況に応じて撃ち分ける。

サイバーパンク × 西部劇。ローポリ／フラットシェーディング。
外部の 3D 素材・テクスチャ・音源に一切依存せず、プリミティブと手続き生成と
シェーダーと Web Audio だけで成立している。

```bash
npm install
npm run dev       # 開発サーバ
npm run build     # 型チェック + 本番ビルド
npm run verify    # Playwright による検証（下記）
```

## 操作

| | |
|---|---|
| WASD | 移動 |
| SPACE | ジャンプ |
| **右クリック長押し** | ボルト(V)が上昇。押している間 FOV が 74°→26° に絞られる |
| **左クリック長押し** | アンペア(A)が上昇。周囲の放電が激しくなる |
| **両方のボタンを離す** | その瞬間に発射。離す順序は自由。押している間は絶対に撃たない |
| R | リロード |
| M | ミュート |
| ` | 調整パネル（leva） |

**V/A 専用のゲージ UI は無い。** ズーム倍率そのものが V のメーター、
周囲の放電の強さそのものが A のメーターを兼ねている。

## 中心にある1つのルール

- **ボルト = 押し出す力** → 弾速・射程・貫通。高Vは直進して敵を貫き、装甲を抜く
- **アンペア = 流す量** → ダメージ・感電範囲・スタン。高Aは遅いが着弾時に周囲へ伝播する
- **電池消費は V × A に比例する**

消費が積なので、**特化した弾は安く、混ぜた弾だけが高い**:

| 撃ち方 | 電圧 | 電流 | 消費 |
|---|---|---|---|
| ボルト全振り | 400V | 1.26A | **12.6** |
| アンペア全振り | 58V | 10.0A | **14.5** |
| 両方全開 | 400V | 10.0A | **100**（単三1本ぶん）|

そして敵3種がそれぞれ別の弾を要求する。装甲個体は 220V 未満を弾き、
群れ個体は感電でまとめて処理するのが圧倒的に安く、高速個体は溜めている時間そのものが損になる。

この設計が本当に成立しているかは目視では確認できないので、
`src/game/economy.ts` が**実際の config と実際の弾道計算で (V,A) 平面を総当たりし**、
各脅威を最安で処理する弾を求める。`npm run verify` はその出力に assert する。
数値をいじって3つの答えが1つに潰れたら、ビルドが落ちる。

実測（`scripts/dev/playthrough.mjs`、god mode でリソースだけを比較）:

| 戦略 | 結果 |
|---|---|
| 常にフルチャージ | **ウェーブ4で電池切れ**（23発 × 100 units）|
| 敵ごとに撃ち分ける | **6ウェーブ完走**、91体撃破、平均 20.7 units/発、予算の約66%で終了 |

## 検証

`npm run verify` は Playwright(chromium) で本番ビルドを開き、24 シナリオ・81 アサーションを実行する。

1. **コンソールエラー / 未捕捉例外 / リクエスト失敗が0件**であること
2. **フレームの輝度標準偏差**が閾値以上であること（単色に近い画面を失敗とする）
3. ゲームの**状態と収支**が正しいこと（チャージ、発射規則、電池コスト、装甲、感電、ウェーブ）

平均輝度では判定しない。意図的に「アリーナを描画しない」故障を入れたとき、
**std=1.13 / mean=4.4** だった。mean は真っ黒でも真っ白でもないので、
平均基準のゲートはこれを通してしまう。

検証そのものが機能することは、3種類の故障を意図的に仕込んで確認済み
（マウント時の例外 / 正常な画面＋console.error 1件 / エラーゼロ＋空のシーン）。
詳細は PROGRESS.md。

CI（`.github/workflows/ci.yml`）は push と PR でこの検証を全部回す。
失敗したフレームのスクリーンショットは常に成果物として上がるので、
「何が描かれていたか」を見て原因を追える。

## 構成

```
src/
  config.ts          全ての調整値（根拠は PROGRESS.md）
  store.ts           zustand。HUD が見る粗い状態だけ
  input.ts           キーボード／マウス／ポインタロック
  game/
    runtime.ts       60Hz で変化する状態（React の外）
    shooting.ts      チャージ→弾の数式、弾プール
    enemies.ts       敵の操舵（物理剛体ではない）
    director.ts      ウェーブ進行
    economy.ts       撃ち分けが成立しているかの解析（verify がこれに assert する）
    effects.ts       パーティクルプール
    audio.ts         Web Audio による実行時合成
  scene/             R3F コンポーネント
  ui/                HUD・タイトル・ポーズ・リザルト・調整パネル
scripts/
  verify.mjs         検証ハーネス
  dev/               開発用の計測スクリプト
```

物理（Rapier）が担当するのは**プレイヤーとアリーナだけ**。
弾と敵は自前ロジックで動かしている。理由は PROGRESS.md に記録した。
